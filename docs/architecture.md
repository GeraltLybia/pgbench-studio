# pgbench studio — архитектура и план реализации

Sep 27, 2026 · @Zakhar Pirozhenko

## Цель и границы MVP

pgbench studio — веб-интерфейс поверх pgbench: подключение к базе, настройка нагрузки и сценариев с проверкой SQL, запуск с прогресс-баром и живыми логами, отчёт с графиками и история запусков. Стек: Vue 3 на фронте, Python (FastAPI) на бэке. Утверждённые макеты: [pgbench UI — дизайн экранов](https://claude.ai/artifact/YPT2c1c7S5m4aAbauXU9Rp), светлая и тёмная тема.

В MVP входит:

- 5 экранов из макетов: Подключение, Нагрузка, Выполнение, Отчёт, История и сравнение.
- Один агент нагрузки: бэкенд и pgbench работают на одной машине, рядом с БД, но не на ней.
- Один запуск за раз на агенте, один-несколько пользователей без ролей.
- Ресурсы (CPU и RAM) снимаются только с машины-агента через psutil.

В MVP не входит: несколько агентов, распределённая нагрузка, роли и SSO, мониторинг ресурсов сервера БД, запуск по расписанию.

Поддерживаемые версии PostgreSQL — 13–18. На агенте один pgbench последней версии (18): он работает со всеми базами из диапазона, и все базы меряются одним клиентом, поэтому их результаты сравнимы.

## Архитектура

Приложение — два контейнера на машине-агенте. nginx в контейнере `frontend` раздаёт собранный фронтенд и проксирует API. FastAPI в контейнере `backend` отвечает на REST, держит WebSocket, проверяет права и запускает pgbench дочерним процессом. Браузер никогда не ходит в БД напрямую.

&#91;embedded content: архитектура · агент нагрузки и серверы БД\]

Браузер через nginx вызывает FastAPI по REST и подписывается на WebSocket запуска. FastAPI проверяет соединение с PostgreSQL через psycopg, а нагрузку подаёт pgbench.

Поток данных во время теста:

1. Фронт отправляет `POST /api/runs` с конфигом нагрузки, получает `run_id`.
2. RunManager создаёт каталог запуска, пишет туда скрипты и стартует pgbench без shell, пароль передаёт через `PGPASSWORD`.
3. stdout и stderr читаются построчно: каждая строка уходит в WS как `log`, строки `progress:` дополнительно разбираются в событие `progress`.
4. Раз в секунду в WS уходит `resources` агента (psutil).
5. После выхода процесса парсеры разбирают итоговый вывод, `-r` и лог `-l`, результаты пишутся в SQLite, в WS уходит `status: completed`.

## Конфигурация

Все настройки агента лежат в одном файле `config.yaml`. Путь к нему задаёт переменная `PGB_STUDIO_CONFIG` (по умолчанию `./config.yaml`). Любое поле можно переопределить переменной окружения с префиксом `PGB_STUDIO_` и разделителем `__`, например `PGB_STUDIO_SERVER__PORT`. Секреты в файл не пишутся: в конфиге указывается только имя переменной окружения, где секрет лежит.

Загрузка через pydantic-settings, конфиг валидируется при старте, ошибка в нём — отказ стартовать с понятным сообщением. Меняется конфиг только перезапуском, из интерфейса он не редактируется.

```yaml
server:
  host: 0.0.0.0                         # внутри сети compose, наружу не публикуется
  port: 8000
  trusted_proxies: [10.0.0.0/24]        # адреса балансировщика: только им верим X-Forwarded-*
  dev_mode: false                       # true — разрешает HTTP и cookie без Secure на localhost
  secret_key_env: PGB_STUDIO_SECRET_KEY # ключ шифрования паролей профилей, обязателен

auth:
  session_ttl_h: 12
  cookie_secure: true                   # HTTPS на балансировщике
  max_failed_logins: 5
  lockout_min: 5
  admin_user_env: PGB_STUDIO_ADMIN_USER         # первый editor, если пользователей нет
  admin_password_env: PGB_STUDIO_ADMIN_PASSWORD

storage:
  sqlite_path: /data/studio.db
  runs_dir: /data/runs                  # логи и файлы каждого запуска
  keep_runs_days: 90

pgbench:
  binary: pgbench                       # или полный путь
  max_parallel_runs: 1
  default_progress_interval_s: 1

agent:
  name: load-agent-01                   # подпись на экране выполнения
  sample_interval_s: 1
  cpu_warning_percent: 85               # выше — предупреждение «упор в генератор»

limits:                                 # защита тестируемой базы и агента
  connections_reserve: 5                # сколько соединений оставить свободными
  max_duration_s: 14400
  max_transactions: 100000000
  max_scale: 5000
  min_free_disk_gb: 5
```

Базы данных в конфиг не попадают: профили подключения создаются в интерфейсе и хранятся в SQLite. Новая база добавляется без перезапуска агента.

### WebSocket `/api/runs/{id}/ws`

Сервер шлёт JSON-сообщения с полями `type`, `seq` и `ts`. При подключении первое сообщение — `snapshot`, поэтому перезагрузка страницы и переподключение ничего не теряют.

| type | Когда | Полезная нагрузка |
| --- | --- | --- |
| `snapshot` | сразу после подключения | статус, конфиг, последние 2000 строк лога, вся серия progress и resources |
| `log` | каждая строка вывода | `stream` (stdout или stderr), `line` |
| `progress` | каждая строка `progress:` | `t`, `tps`, `lat_ms`, `stddev_ms`, `lag_ms`, `failed`, `pct`, `eta_s` |
| `resources` | раз в 1 с | `source`, `cpu_pct`, `ram_pct`, `ram_used_bytes`, `ram_total_bytes` |
| `warning` | CPU агента выше порога | `code`, `message` |
| `status` | смена статуса | `status`, `exit_code`, `error` |

Жизненный цикл запуска: `queued` → `running` → `finalizing` (разбор логов) → `completed`, `failed` или `cancelled`.

### Раннер pgbench

- `command.py` собирает argv из `RunConfig`, всегда добавляя `-P <interval> -r -l --log-prefix=<run_dir>/pgbench_log`. В обычном режиме к ним добавляется `--aggregate-interval=1`, в подробном — нет.
- Параметры подключения передаются через env: `PGHOST`, `PGPORT`, `PGUSER`, `PGDATABASE`, `PGPASSWORD`, `PGSSLMODE`, `PGAPPNAME`, `PGCONNECT_TIMEOUT`. В argv и логах пароля нет.
- Процесс запускается `asyncio.create_subprocess_exec`, stdout и stderr читаются параллельно. Всё пишется в `stdout.log` и `stderr.log` в каталоге запуска и в кольцевой буфер для WS.
- Прогресс: в режиме `-T` — `t / T`. В режиме `-t` — накопленные `tps × интервал` против `c × t`, в интерфейсе с пометкой «оценка». Для `pgbench -i` разбираются строки `N of M tuples (x%) done`.
- Отмена: SIGINT, через 5 с SIGTERM, ещё через 5 с SIGKILL. Частичные логи разбираются, статус `cancelled`.
- При старте бэкенда запуски в статусе `running` помечаются как `failed` с причиной «агент перезапущен».

### Парсеры

- Регулярки рассчитаны на формат pgbench 18, включая поля `failed`, `retried` и `skipped` в строках `progress:`, итоговом выводе, логе `-l` и выводе `-r`. Формат вывода задаёт клиент, поэтому от версии сервера он не зависит.
- Лог `--aggregate-interval` при `-j > 1` пишется файлом на поток. Файлы сливаются по `interval_start` суммированием счётчиков, min и max берутся по всем файлам.
- Подробный режим: лог каждой транзакции читается потоково. Строятся посекундные агрегаты и гистограмма latency с логарифмическими корзинами, из неё p50, p95, p99. Сырой лог после разбора сжимается gzip. Есть опция `--sampling-rate` для гистограммы.
- Каждый парсер покрыт тестами на реальных выводах pgbench 18 против серверов 13 и 18 из `tests/fixtures`.

### Валидатор сценариев

1. Текст делится на команды: мета-команды начинаются с `\`, SQL-команды заканчиваются `;`.
2. Мета-команды проверяются по списку pgbench 18: `\set`, `\setshell`, `\shell`, `\sleep`, `\if`, `\elif`, `\else`, `\endif`, `\gset`, `\aset`, `\startpipeline`, `\syncpipeline`, `\endpipeline`. Проверяется число аргументов и парность `\if` и `\endif`. Мета-команды выполняет сам клиент, поэтому они доступны для баз любой версии. SQL же выполняет сервер, поэтому валидатор учитывает мажорную версию базы из последней проверки соединения: узлы AST из более новых версий (например `MergeStmt` — PostgreSQL 15, `JsonTable` — PostgreSQL 17) дают ошибку «не поддерживается в PostgreSQL N». Таблица таких узлов ведётся в `validator.py`, остальное ловит пробный прогон.
3. Переменные `:name` заменяются литералом, SQL разбирается `pglast.parse_sql`. Ошибка переводится в строку и колонку исходного текста.
4. Неизвестная переменная (не задана `\set`, не `:scale`, не `:client_id`) — предупреждение, не ошибка: её может задать `-D`.
5. Ответ — список `{line, col, end_col, severity, message}`, по нему фронт рисует маркеры в редакторе.

### Проверка подключения

Дальше экрана «Подключение» пользователь проходит только после успешной проверки соединения с текущими параметрами. При ошибке сценарий останавливается.

- Кнопка «Далее: нагрузка» и пункты меню «Нагрузка», «Выполнение», «Отчёт» неактивны, пока нет успешной проверки. Прямой переход по URL перехватывает router guard и возвращает на `/connect`. История остаётся доступна всегда.
- Любое изменение полей формы или смена профиля сбрасывает результат проверки, её нужно пройти заново.
- При открытии приложения с сохранённым профилем проверка запускается автоматически.
- Результат хранится в `useProfilesStore` вместе с хешем параметров, с которыми он получен. Несовпадение хеша считается «не проверено».
- При ошибке карточка справа показывает понятную причину и подсказку, исходный текст ошибки PostgreSQL раскрывается по клику.

Бэкенд классифицирует ошибку `POST /api/profiles/test` и возвращает `{ok: false, code, message, hint, raw}`:

| code | Причина | Подсказка пользователю |
| --- | --- | --- |
| `host_unreachable` | хост не найден или не отвечает | проверить адрес и сеть до агента |
| `timeout` | превышен таймаут подключения | проверить доступность и увеличить таймаут |
| `connection_refused` | порт закрыт | проверить порт и что PostgreSQL слушает этот адрес |
| `auth_failed` | неверный пользователь или пароль | проверить логин, пароль и pg\_hba.conf |
| `database_not_found` | базы не существует | проверить имя базы |
| `no_connect_privilege` | нет права CONNECT | выдать права пользователю |
| `ssl_error` | ошибка SSL | сменить SSL mode или проверить сертификат |
| `unknown` | прочее | показать исходный текст ошибки |

Сервер новее pgbench на агенте или старше 13 — предупреждение, оно не блокирует переход. Бэкенд тоже защищается сам: `POST /api/runs` и `POST /api/profiles/{id}/init` перед стартом повторяют проверку соединения и при ошибке отвечают `422` с той же структурой, процесс pgbench не запускается.

### Состояние (Pinia)

- `useSystemStore` — health, версия pgbench, порог CPU.
- `useProfilesStore` — профили и активный профиль, результат проверки соединения.
- `useLoadConfigStore` — черновик настроек нагрузки и сценариев. Сохраняется в `localStorage`, переживает перезагрузку.
- `useRunStore(id)` — подписка на WS: статус, лог (кольцевой буфер 5000 строк), серии progress и resources, предупреждения. Переподключение с экспоненциальной задержкой, при каждом подключении состояние заменяется `snapshot`.

### Компоненты

- Оболочка: `AppSidebar` с пунктами меню, карточкой подключения и переключателем темы, `PageHeader`.
- Формы: `FieldInput`, `SegmentedControl`, `ProfileSelect`, `ConfirmByTyping` (подтверждение `pgbench -i` вводом имени базы).
- Нагрузка: `ScenarioList` (перетаскивание, веса, доля в %), `ScriptEditor`, `CommandPreview`.
- Выполнение: `RunProgress`, `KpiTile`, `LiveChart`, `ResourcePanel`, `LogConsole` (виртуальный список, фильтры, автопрокрутка, скачивание).
- Отчёт: `TimeSeriesChart`, `LatencyBandChart`, `StatementBars`, `LatencyHistogram`, `RawOutput`, `RunParams`.
- История: `RunsTable`, `Sparkline`, `CompareOverlay`.

### Редактор сценариев

Подсветка SQL плюс отдельная подсветка мета-команд `\...` и переменных `:name`. Текст отправляется на `/api/scripts/validate` через 400 мс после последнего изменения. Диагностики превращаются в маркеры `@codemirror/lint` с подсказкой при наведении. Кнопка «Запустить тест» заблокирована, пока в любом сценарии есть ошибка.

### Темы

Цвета из макетов оформляются токенами в `tokens.css`: `:root` — светлая тема, `[data-theme="dark"]` — тёмная. По умолчанию тема берётся из `prefers-color-scheme`, выбор пользователя запоминается. Графики читают цвета серий из тех же CSS-переменных и перерисовываются при смене темы.

### Живой график

Ось X — вся длительность теста в режиме `-T`, будущее закрашено фоном с подписью «осталось N с». Точки добавляются без полной перерисовки. При длинных тестах, больше 3600 точек, включается прореживание LTTB.

## Модель данных

Всё хранится в одной базе SQLite плюс каталог файлов на каждый запуск. Схема ведётся миграциями Alembic.

| Таблица | Ключевые поля | Назначение |
| --- | --- | --- |
| `profiles` | name, host, port, dbname, user, sslmode, app\_name, connect\_timeout\_s, password\_enc | профили подключения |
| `scripts` | name, body, updated\_at | библиотека своих сценариев |
| `runs` | profile\_id, started\_by, stopped\_by, confirmed\_rules\_json, kind (init или bench), status, config\_json, argv\_json, started\_at, finished\_at, server\_version, pgbench\_version, summary\_json, error, note | запуск и его итог |
| `run_series` | run\_id, t\_s, tx, tps, lat\_avg\_ms, lat\_min\_ms, lat\_max\_ms, lat\_std\_ms, lag\_ms, failed, retried | посекундный ряд из лога `-l` |
| `run_statements` | run\_id, script, idx, sql, latency\_ms, failures | задержки по запросам из `-r` |
| `run_histogram` | run\_id, bucket\_upper\_ms, count | гистограмма latency, только в подробном режиме |
| `run_resources` | run\_id, t\_s, cpu\_pct, ram\_pct, ram\_used\_bytes | ресурсы агента во время теста |

`summary_json` хранит итоговые метрики из вывода pgbench: tps, latency avg и stddev, число транзакций, failed, время подключения, p50, p95 и p99 при наличии. В `config_json` лежит полный `RunConfig` вместе с текстами сценариев на момент запуска, поэтому «Повторить» воспроизводит тест точно, даже если сценарий потом изменили.

Каталог `runs_dir/<run_id>/` содержит файлы сценариев, `stdout.log`, `stderr.log` и логи `pgbench_log.*` (в подробном режиме сжатые gzip). Запуски старше `keep_runs_days` удаляются фоновой задачей раз в сутки вместе с файлами.

Пароли профилей хранятся зашифрованными (Fernet) ключом `PGB_STUDIO_SECRET_KEY`, без ключа бэкенд не стартует. Для входа добавляются таблицы `users` (username, password\_hash, role, disabled, failed\_attempts, locked\_until, last\_login\_at) и `sessions` (token\_hash, user\_id, expires\_at).

## Развёртывание

Фронт и бэк — два контейнера на одной машине-агенте, связанные через `docker-compose.yml`. Наружу открыт только порт контейнера фронта, бэкенд доступен лишь во внутренней сети compose.

| Контейнер | Образ | Что внутри | Порт |
| --- | --- | --- | --- |
| `frontend` | `nginx:alpine` + собранный SPA | раздача статики, проксирование `/api/*` и WebSocket на бэкенд | 8080 наружу |
| `backend` | `python:3.12-slim` + `postgresql-client-18` | FastAPI, pgbench 18, SQLite | 8000 только внутри сети |

- nginx проксирует `/api/` на `http://backend:8000`, для WebSocket передаёт заголовки `Upgrade` и `Connection`, таймаут чтения для WS — не меньше максимальной длительности теста.
- Для браузера всё приходит с одного origin, поэтому CORS на бэкенде выключен.
- Тома: `./data` (SQLite, файлы запусков) и `./config.yaml` только для чтения монтируются в `backend`. Контейнер `frontend` состояния не хранит.
- Секреты (`PGB_STUDIO_SECRET_KEY`, пароль первого администратора) передаются через `.env` или Docker secrets, в образ не попадают.
- У обоих контейнеров есть `healthcheck` (см. раздел «Health check»), `frontend` стартует после того, как `backend` стал `healthy`, и оба с `restart: unless-stopped`.
- Версии образов собираются в CI и тегируются одной версией приложения, чтобы фронт и бэк не разъезжались.

### HTTPS

HTTPS терминируется на корпоративном балансировщике перед машиной агента, сертификат обслуживает команда инфраструктуры. От балансировщика до nginx трафик идёт по HTTP внутри дата-центра.

Что нужно от балансировщика — согласовать с инфраструктурой до этапа 0:

- проксировать всё на порт `frontend` (8080) и передавать заголовки `X-Forwarded-Proto`, `X-Forwarded-For`, `X-Forwarded-Host`;
- пропускать WebSocket: заголовки `Upgrade` и `Connection`, таймаут простоя не меньше максимальной длительности теста (`limits.max_duration_s`, по умолчанию 4 ч). Если столько не дают, фронт шлёт ping раз в 30 с, а таймаут должен быть больше 30 с;
- перенаправлять `http://` на `https://`, включить HSTS;
- разрешить доступ к порту 8080 машины агента только с адресов балансировщика (firewall или security group), чтобы обойти его напрямую было нельзя.

Что настраивается у нас:

- nginx доверяет `X-Forwarded-*` только от адресов из `server.trusted_proxies` (`set_real_ip_from`, `real_ip_header X-Forwarded-For`) и пробрасывает их бэкенду.
- uvicorn запускается с `--proxy-headers --forwarded-allow-ips=<адрес контейнера frontend>`: так FastAPI видит реальную схему `https` и IP клиента.
- Cookie сессии — `Secure`, `HttpOnly`, `SameSite=Strict`. Флаг `Secure` по умолчанию включён и выключается только в dev-режиме для `localhost`.
- Бэкенд отклоняет изменяющие запросы, если `X-Forwarded-Proto` не `https` (кроме dev-режима): это страхует от случайной публикации в обход балансировщика.
- В логах приложения, в истории входов и в блокировке после неудачных попыток используется реальный IP клиента, а не адрес балансировщика.

## Роли и доступ

Вход по логину и паролю обязателен, анонимного доступа нет. Три роли: `viewer` (чтение), `editor` (редактирование и запуск) и `admin` (всё, что может `editor`, плюс управление пользователями из интерфейса).

| Действие | viewer | editor | admin |
| --- | --- | --- | --- |
| История, отчёты, сравнение | да | да | да |
| Наблюдение за идущим тестом: прогресс, логи, ресурсы | да | да | да |
| Просмотр профилей подключения (без паролей) | да | да | да |
| Создание, изменение, удаление профилей | нет | да | да |
| Проверка соединения, `pgbench -i` | нет | да | да |
| Библиотека сценариев: изменение | нет | да | да |
| Запуск, пробный прогон, остановка теста | нет | да | да |
| Удаление запусков из истории | нет | да | да |
| Управление пользователями: создание, роли, блокировка, сброс пароля | нет | нет | да |
| Смена собственного пароля | да | да | да |

Реализация:

- Пользователи хранятся в таблице `users`: логин, хеш пароля (argon2id через `argon2-cffi`), роль, признак блокировки, время последнего входа.
- Первый `admin` создаётся при старте из переменных `PGB_STUDIO_ADMIN_USER` и `PGB_STUDIO_ADMIN_PASSWORD`, если таблица пуста. Дальше пользователями управляет администратор на экране «Пользователи» (`/admin/users`): создаёт учётки с временным паролем, меняет роль, блокирует, сбрасывает пароль. При первом входе с временным паролем система требует его сменить. CLI `studio users reset-admin` в контейнере бэкенда остаётся только для аварийного восстановления доступа.
- API пользователей — только для `admin`: `GET/POST /api/users`, `PATCH /api/users/{id}` (роль, блокировка), `POST /api/users/{id}/reset-password`. Смена своего пароля — `POST /api/auth/password` для любой роли. Нельзя заблокировать или понизить последнего активного `admin`, и администратор не может понизить сам себя.
- `POST /api/auth/login` выдаёт сессию в cookie `HttpOnly`, `Secure`, `SameSite=Strict`, срок жизни задаётся в конфиге (по умолчанию 12 ч). `POST /api/auth/logout`, `GET /api/auth/me` возвращает логин и роль.
- Права проверяются на бэкенде зависимостью FastAPI на каждом эндпоинте и при подключении к WebSocket. `viewer` на запрещённое действие получает `403`.
- Фронт по роли из `/api/auth/me` скрывает или блокирует кнопки редактирования и запуска, но это только удобство, защита — на бэкенде.
- Неудачные попытки входа ограничены: после 5 подряд логин блокируется на 5 минут. Попытки считаются по логину и по реальному IP клиента из X-Forwarded-For, а не по адресу балансировщика.
- В `runs` записывается, кто запустил или остановил тест, это видно в истории и отчёте.

Пароли профилей подключения хранятся в SQLite зашифрованными (Fernet). Ключ `PGB_STUDIO_SECRET_KEY` обязателен: без него бэкенд не стартует. Пароль профиля никогда не возвращается в API, форма показывает только «пароль сохранён» и даёт его заменить.

## Защита тестируемой базы

Цель — не положить базу и не испортить данные случайно. Проверки работают в два слоя. Фронт валидирует форму и сценарии сразу при вводе и не даёт отправить опасную конфигурацию без явного подтверждения. Бэкенд повторяет те же проверки при `POST /api/runs` и отклоняет запрос с `422`, даже если фронт обойти.

### Параметры нагрузки

Схема формы описана на фронте через zod и повторяет pydantic-модель `RunConfig`. Лимиты приходят с бэкенда из `config.yaml` (секция `limits`) и из последней проверки соединения.

| Проверка | Ошибка, запуск заблокирован | Предупреждение, нужно подтвердить |
| --- | --- | --- |
| Клиенты `-c` против свободных соединений | больше свободных `max_connections` минус резерв | больше 80 % свободных |
| Потоки `-j` | больше `-c` или больше числа ядер агента | — |
| Длительность `-T` | меньше 10 с или больше `limits.max_duration_s` (по умолчанию 4 ч) | больше 1 ч |
| Транзакции `-t` | `c × t` больше `limits.max_transactions` | — |
| Rate `-R`, latency limit | ноль или отрицательное значение | — |
| Scale для `pgbench -i` | больше `limits.max_scale` | оценка объёма данных больше 50 ГБ |
| Профиль | нет успешной проверки соединения | сервер вне диапазона 13–18 |

### Сценарии

Валидатор на бэкенде разбирает SQL через pglast и помечает опасные конструкции по дереву запроса, а не по тексту: так правило не срабатывает на слово `DROP` в комментарии или строке. Фронт показывает эти пометки в редакторе и в сводке перед запуском.

| Уровень | Что ловится | Поведение |
| --- | --- | --- |
| Запрещено | `DROP DATABASE`, `DROP ROLE`, `ALTER SYSTEM`, `CREATE`/`ALTER ROLE`, `pg_terminate_backend`, `pg_cancel_backend`, `pg_reload_conf`, `COPY … TO/FROM PROGRAM`, `\shell`, `\setshell` | запуск невозможен ни для кого |
| Опасно | `DROP TABLE`, `TRUNCATE`, `ALTER TABLE`, `VACUUM FULL`, `CLUSTER`, `REINDEX`, `DELETE` и `UPDATE` без `WHERE`, `LOCK TABLE` | запуск только после подтверждения: чекбокс с перечнем найденного |
| Внимание | запись в таблицы, кроме `pgbench_*`; явные `BEGIN` без `END` | пометка в редакторе, подтверждение не нужно |

- Перед каждым запуском показывается сводка: база и сервер, нагрузка, сценарии с весами, найденные предупреждения. Кнопка «Запустить» в ней активна только после подтверждения всех пунктов уровня «Опасно».
- Подтверждение записывается в `runs` вместе с перечнем подтверждённых правил: видно, кто и что сознательно разрешил.
- Пробный прогон подчиняется тем же правилам.
- `\shell` и `\setshell` запрещены, потому что выполняют команды на машине агента, а не в базе.
- В документации к инструменту рекомендуется отдельный пользователь БД без прав суперпользователя: это последний рубеж, если правило что-то пропустит.

## Health check

Состояние системы проверяется на трёх уровнях: жив ли процесс, готов ли он работать и что именно не так. Первые два нужны Docker и мониторингу, третий — людям в интерфейсе.

| Эндпоинт | Доступ | Что проверяет | Ответ |
| --- | --- | --- | --- |
| `GET /healthz` | без авторизации | процесс отвечает | `200 {"status":"ok"}` |
| `GET /readyz` | без авторизации | все обязательные проверки ниже | `200`, либо `503` со списком проваленных |
| `GET /api/system/health` | `viewer` и выше | подробный отчёт по каждой проверке | статус, значение, порог, сообщение |

Проверки бэкенда:

| Проверка | Обязательная | Ошибка, если |
| --- | --- | --- |
| Конфиг загружен и валиден | да | не прошёл валидацию при старте |
| Ключ шифрования задан | да | нет `PGB_STUDIO_SECRET_KEY` |
| SQLite открывается на запись, миграции применены | да | ошибка записи или версия схемы отстаёт |
| Каталог `runs_dir` доступен на запись | да | нет прав или каталога |
| Свободное место на томе `./data` | да | меньше `limits.min_free_disk_gb` (предупреждение при двойном пороге) |
| pgbench найден, версия определяется | да | нет бинарника или `pgbench --version` не отвечает |
| Нагрузка на агент: CPU, RAM | нет | предупреждение, если выше порогов из конфига |
| Зависшие запуски | нет | запуск в `running` без живого процесса |

- Контейнер `backend`: Docker `healthcheck` вызывает `/readyz` каждые 15 с. Контейнер `frontend`: nginx отдаёт свой `/healthz` и проверяет, что бэкенд за прокси отвечает на `/healthz`.
- В интерфейсе в боковом меню — индикатор состояния системы: зелёный, жёлтый (есть предупреждения), красный (не пройдена обязательная проверка). По клику открывается список проверок из `/api/system/health`.
- Если обязательная проверка не пройдена, запуск тестов блокируется с понятной причиной, просмотр истории остаётся доступен.
- Проверки `/readyz` дешёвые и кешируются на 5 с, чтобы частые пробы не нагружали агент.

## Тестирование

Unit-тесты бэкенда обязательны и пишутся вместе с кодом каждого этапа, а не в конце. CI не пропускает merge, если тесты падают или покрытие ниже порога.

### Unit-тесты бэкенда (pytest)

| Модуль | Что проверяется |
| --- | --- |
| `core/command.py` | argv для каждой комбинации параметров, пароль не попадает в argv, экранирование путей |
| `core/parsers/*` | разбор реальных выводов pgbench 18: progress, итог, `-r`, агрегированный и по-транзакционный лог, слияние логов потоков, прерванный и отменённый запуск |
| `core/validator.py` | мета-команды, ошибки SQL с правильной строкой и колонкой, правила опасных конструкций по уровням, учёт версии сервера |
| Проверки нагрузки | каждый лимит из таблицы «Параметры нагрузки»: граница, чуть ниже, чуть выше |
| Классификатор ошибок соединения | каждый код из таблицы проверки подключения |
| `core/runner.py` | жизненный цикл, отмена с эскалацией сигналов, восстановление после рестарта — на фейковом pgbench-скрипте |
| Авторизация | матрица прав: каждый эндпоинт под `viewer`, `editor` и без входа; блокировка после неудачных попыток |
| `storage/crypto.py`, конфиг | шифрование паролей, отказ старта без ключа, валидация `config.yaml` |
| Health check | каждая проверка в состоянии ok, warning и fail |

Порог покрытия — 85 % строк для `core/` и `api/`, 70 % для остального кода, отчёт `pytest-cov` в CI.

### Остальные уровни

- **Интеграционные тесты бэкенда** — pytest с Testcontainers: настоящий pgbench 18 против PostgreSQL 13 и 18, инициализация, короткий тест, отмена, разбор результатов.
- **Фронтенд, Vitest** — схемы валидации формы и все лимиты, сторы, форматтеры, реакция редактора на диагностики, скрытие действий для `viewer`.
- **E2E, Playwright** — вход под `editor` и `viewer`, проверка соединения с ошибкой и успехом, блокировка опасного сценария, 30-секундный тест, отчёт, сравнение.

## Безопасность и эксплуатация

Инструмент позволяет выполнять произвольный SQL на подключённой базе, поэтому доступ к нему закрыт так же строго, как к самой базе.

- Наружу опубликован только порт nginx, бэкенд доступен лишь во внутренней сети compose. Вход обязателен, права по ролям проверяются на бэкенде.
- pgbench запускается только через `create_subprocess_exec` со списком аргументов. Значения из форм валидируются pydantic (порты, числа, sslmode из перечня), имена файлов сценариев генерирует бэкенд.
- Пароль БД живёт только в env дочернего процесса. В argv, логах, ответах API и WS он не появляется, в превью команды замаскирован.
- `pgbench -i` требует подтверждения вводом имени базы. В документации к инструменту рекомендуется отдельный пользователь БД под тесты, не суперпользователь.
- Пробный прогон предупреждает, что запросы выполняются по-настоящему.
- Фронт и API приходят с одного origin через nginx, CORS выключен, WS принимает только тот же origin и только с действующей сессией.

Эксплуатация:

- Два образа, подробности в разделе «Развёртывание»: `frontend` (nginx + собранный SPA) и `backend` (Python + `postgresql-client-18` из репозитория PGDG, версия задаётся аргументом `PG_MAJOR=18`). С выходом новой мажорной версии PostgreSQL образ бэкенда пересобирается с новым клиентом.
- `docker-compose.yml` для разработки: агент и две тестовые базы, PostgreSQL 13 и 18.
- Тома: `./data` (SQLite и запуски), `./config.yaml` только для чтения.
- Проверка совместимости: при тесте соединения запоминается мажорная версия сервера. Если сервер новее pgbench на агенте или старше 13, показывается предупреждение.
- Логи самого приложения — JSON в stdout, уровень задаётся в конфиге.

## План реализации

Шесть этапов, каждый заканчивается работающим срезом, который можно показать. Следующий этап начинается после того, как выполнены все критерии приёмки текущего. Общий критерий для каждого этапа — unit-тесты на новый код бэкенда с порогом покрытия из раздела «Тестирование». Эталон вёрстки — макеты на холсте, в обеих темах.

### Этап 0. Каркас

Монорепозиторий `backend/` + `frontend/`, загрузка конфига, Docker, CI.

- [ ] `docker compose up` поднимает агент и тестовые базы PostgreSQL 13 и 18.
- [ ] Контейнеры `frontend` и `backend` проходят healthcheck, `/healthz` и `/readyz` отвечают, индикатор состояния в меню работает.
- [ ] Вход под `editor` и `viewer`, матрица прав покрыта unit-тестами, `viewer` получает `403` на изменяющие запросы.
- [ ] Администратор из интерфейса создаёт пользователей, меняет роли, блокирует и сбрасывает пароли. Временный пароль требует смены при первом входе, последнего `admin` заблокировать нельзя.
- [ ] Через балансировщик: вход по HTTPS, cookie с флагом `Secure`, WebSocket не обрывается на тесте длиной 1 ч, в логах и блокировке виден реальный IP клиента. Прямой запрос к машине в обход балансировщика не проходит.
- [ ] Приложение открывается на `localhost:8080`: боковое меню, пустые экраны, переключатель темы работает.
- [ ] Ошибка в `config.yaml` останавливает старт с понятным сообщением.
- [ ] CI гоняет ruff, mypy, pytest с порогом покрытия, ESLint, vue-tsc и Vitest.

### Этап 1. Подключение

Профили, проверка соединения, инициализация данных.

- [ ] CRUD профилей, пароль хранится зашифрованным или не хранится, если ключа нет.
- [ ] «Проверить соединение» показывает версию сервера, совместимость pgbench, `max_connections`, наличие таблиц `pgbench_*` и примерный scale.
- [ ] Без успешной проверки соединения перейти на «Нагрузку» нельзя ни кнопкой, ни через меню, ни по URL. Каждая ошибка из таблицы кодов показывается с понятной причиной и подсказкой.
- [ ] pgbench 18 инициализирует данные и проводит тест на базах PostgreSQL 13 и 18.
- [ ] `pgbench -i` запускается только после ввода имени базы, прогресс инициализации виден в интерфейсе.

### Этап 2. Нагрузка и валидатор

Форма нагрузки, список сценариев, редактор, превью команды.

- [ ] Все параметры из макета собираются в `RunConfig`, превью команды совпадает с тем, что реально запустится.
- [ ] Ошибка SQL подсвечивается на нужной строке меньше чем через секунду после ввода.
- [ ] Незакрытый `\if` и неизвестная мета-команда дают ошибку, неизвестная переменная — предупреждение.
- [ ] Кнопка запуска заблокирована при ошибках, пробный прогон работает.

* [ ] Лимиты нагрузки и правила опасных конструкций работают на фронте при вводе и повторно на бэкенде: конфигурация, запрещённая правилами, возвращает `422` даже в обход интерфейса.
* [ ] Сводка перед запуском требует подтвердить каждое «опасное» правило, подтверждения сохраняются в запуске.

### Этап 3. Запуск и живой мониторинг

RunManager, WebSocket, экран выполнения.

- [ ] Прогресс-бар, оставшееся время и время окончания точны в режиме `-T`.
- [ ] Живые логи и график обновляются раз в секунду. После перезагрузки страницы всё восстанавливается из `snapshot`.
- [ ] «Остановить» завершает pgbench не дольше чем за 10 с, статус `cancelled`.
- [ ] Панель агента показывает CPU и RAM раз в секунду. Предупреждение появляется при CPU выше порога.
- [ ] Второй запуск при активном первом получает `409` и понятное сообщение.

### Этап 4. Отчёт

Парсеры, сохранение, экран отчёта.

- [ ] Итоговые метрики совпадают с выводом pgbench до последнего знака.
- [ ] Графики TPS и latency строятся из лога `-l`, корректно при `-j > 1`.
- [ ] Задержки по запросам из `-r`, сырой вывод и параметры запуска на экране.
- [ ] В подробном режиме есть гистограмма и p50, p95, p99.
- [ ] Парсеры проходят тесты на выводах pgbench 18 против серверов 13 и 18, включая ошибки транзакций и запуск с -j > 1.

### Этап 5. История и сравнение

- [ ] Ряд ресурсов агента сохраняется и показывается в отчёте рядом с TPS.
- [ ] История с поиском и фильтрами, «Повторить» открывает нагрузку с теми же параметрами и сценариями.
- [ ] Сравнение двух запусков: наложенные графики и разница в процентах.

- [ ] Все экраны сверены с макетами в светлой и тёмной теме.
